# Scheduler coordination: historical precedent and recommendation

Research date: 2026-09-16. Design research only; no implementation. Question: which coordination guarantees let this plugin refill worker slots and integrate several epics without duplicate work or dependence on an interactive supervisor?

Confirmed scope: multiple worker hosts and whole-machine failure recovery from the first release. The single-host discussion below explains a weaker guarantee for comparison; it is not the recommended production starting point. The [controller proposal](dispatch-controller.md) defines the release requirements and storage/fencing prerequisites.

## Existing foundation

`scripts/dispatch-next.sh` fills slots from the task ordering, but reads the running count before launching; concurrent invocations can each observe the same free capacity. `scripts/watch.py` combines observation with gate checks, PR closure and review resumption every ten seconds. It exits when no worker is running and no task is ready, even if external gates remain pending. `scripts/merge-queue.sh` already partitions merge ownership by destination branch, but its ensure path creates the bead and publishes its key in separate steps. The remote-worker document is explicitly a hypothesis, not evidence that shared-store coordination is implemented.

## Verified historical mechanisms

- **Marathon used active/passive scheduling.** Multiple scheduler instances ran with one ZooKeeper-elected leader; followers forwarded API requests. Its documented ZooKeeper session timeout caused the leader to abdicate after loss of its session. This is failover of the decision maker, not concurrent scheduling by every observer. Sources: [D2iQ HA documentation](https://archive-docs-old.d2iq.com/mesosphere/dcos/1.13/overview/high-availability/), [Marathon 1.7 flags](https://d2iq-archive.github.io/marathon/1.7/docs/command-line-flags.html).
- **The transferable Mesos pattern is durable intent, identity and reconciliation.** Persist launch intent durably before launch; retain framework identity through failover; reconcile before replacing uncertain tasks. Ordinary messages can be lost. Agent-persisted status updates are retried until acknowledged and may arrive more than once, so handlers must be idempotent. Existing tasks can survive scheduler unavailability. A partitioned worker may still run and contact external systems, making an automatic replacement potentially concurrent with it. Source: [Mesos HA framework guide](https://mesos.apache.org/documentation/latest/high-availability-framework-guide/).
- **Events did not eliminate repair sweeps.** Mesos recommends reconciliation after registration/failover and periodically, with bounded exponential backoff and only one reconciliation in progress. Marathon 1.7 documented a ten-minute reconciliation period. Those historical defaults are not proposed plugin intervals. Sources: [Mesos reconciliation](https://mesos.apache.org/documentation/latest/reconciliation/), [Marathon flags](https://d2iq-archive.github.io/marathon/1.7/docs/command-line-flags.html).
- **Application election and consensus are separate layers.** ZooKeeper's election recipe creates ephemeral sequential nodes, elects the lowest sequence, and watches only the predecessor to avoid waking all contenders. Its replicated service orders writes through quorums and leadership epochs; read operations can be stale. Copying the election recipe without the underlying consistency guarantees would not reproduce its safety. Sources: [ZooKeeper recipes](https://zookeeper.apache.org/doc/r3.7.2/recipes.html#sc_leaderElection), [ZooKeeper internals](https://zookeeper.apache.org/doc/current/zookeeperInternals).
- **Fencing must reach the resource.** BookKeeper illustrates this concretely: storage servers reject writes from the former writer after recovery fences the ledger. Merely updating leadership metadata would not prevent the former writer from writing. Source: [Apache BookKeeper fencing](https://cwiki.apache.org/confluence/display/BOOKKEEPER/Fencing).

## Recommendation for this plugin

These are design deductions from the sources and local code, not existing guarantees:

1. Use a reconciliation engine awakened by committed task changes, worker exits, gate results and capacity changes. Its task graph is repository-scoped, but admission must share one authority across every repository using the same capacity pool. Notifications request another pass; persisted state determines the action. Coalesce wakeups and retain a slow recovery sweep. An interactive session should observe this engine, not be required for progress.
2. Atomically reserve capacity and claim a unique task attempt before launching. Persist an operation identifier and pending launch intent. Recover an uncertain launch by checking the runner for that identity; blindly replaying it can duplicate an expensive worker. Terminal events release reservations exactly once through idempotent transitions. A lease timeout alone is not proof that a worker stopped.
3. On one machine, an OS-supervised controller plus a process-scoped exclusive lock can prevent concurrent controllers and restart after crashes. This tolerates process failure; the machine and local durable store remain failure domains. Do not call this host-level HA.
4. For host-level HA, use replaceable controllers on different hosts and a shared authoritative store with tested conditional writes, durable claims and HA. Elect one active controller with an established coordination service; do not build a bespoke election algorithm. A single shared Dolt server would still be a failure point. Backend selection needs a separate availability and operational-cost decision.
5. Give each task attempt a generation, and require its current generation at state transitions and side effects. Integration must verify both current ownership and the expected destination revision. A metadata lease or client-side pre-check cannot fence a paused old process that later resumes a push. Publication needs enforcement at the destination or a fenced publication service; unavailable enforcement means recovery must wait for confirmed termination. Fast-forward rejection prevents some conflicting publications, not every stale-owner publication.
6. Preserve queues per destination branch. Separate epic targets may test and integrate concurrently; one destination requires ordered publication. For batching, build a candidate containing several selected epic heads on an exact base revision, test that candidate, then publish only if the base and selected heads still match. A failed batch can split to identify the offending subset; a changed base requires rebuilding and revalidation. Track the candidate as durable work so controller failover cannot lose its outcome.

The useful guarantee is one accepted owner and one accepted publication per operation, with retryable processing. Preventing overlapping live worker attempts during a network partition conflicts with prompt replacement unless the previous execution can be fenced or confirmed stopped. Even then, checkpoint replay can repeat work and an outstanding provider request can outlive its client; zero repeated computation or duplicate provider billing is not established by runner fencing.

Context7 was tried first; its Marathon result referred to an unrelated mobile test runner. The primary sources above describe historical Mesos/Marathon behavior. No library adoption is recommended here; Marathon is archived and Mesos is retired.
